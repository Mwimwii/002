# Feature Specification: Groupee - Core Messaging and Paywalled Sharing

**Feature Branch**: `groupee-core-messaging`  
**Created**: 2025-10-24  
**Status**: Draft  
**Input**: User description: "Develop Groupee, a decentralized messaging and paywalled file-sharing app. It must allow users to connect their wallets to log in. In this initial phase, let's call it "Core Messaging and Paywalled Sharing." Users should be able to create a new group chat. Users in a group can send and receive basic text messages using XMTP. The core feature is the ability to attach a file (up to 50MB for the prototype) to a message, which is uploaded to IPFS via Pinata. When a file is attached, the user must be able to set an arbitrary price (in ETH or a test token) that other users must pay to download the file. The message content should be viewable, but the file attachment should only be accessible/downloadable after a successful payment via an x402 link generated by the Hono server. The payment link should be displayed prominently next to the file name in the chat. A user who has paid should not be prompted to pay again for the same file."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Wallet Connection and Authentication (Priority: P1)

User connects their cryptocurrency wallet to authenticate with the Groupee application and access features.

**Why this priority**: Core functionality required for any other feature to work; establishes identity and payment capability.

**Independent Test**: User can successfully connect their wallet, authenticate, and see their profile in the application.

**Acceptance Scenarios**:

1. **Given** user has an installed wallet (MetaMask/Mobile), **When** user clicks "Connect Wallet", **Then** wallet connection prompt appears and user can authenticate
2. **Given** user disconnected wallet, **When** user tries to access messaging features, **Then** user is redirected to wallet connection

---

### User Story 2 - Group Creation and Management (Priority: P1)

User creates and manages group chats with other wallet addresses, with automatic admin privileges upon creation.

**Why this priority**: Enables the core messaging functionality that allows file sharing between multiple users, with proper access controls.

**Independent Test**: User can create a new group (becoming admin), add members, remove members, and send a basic text message to the group.

**Acceptance Scenarios**:

1. **Given** authenticated user, **When** user creates new group, **Then** group is created, user becomes admin, and can invite others via wallet address
2. **Given** user is group admin, **When** user removes member, **Then** member is removed from group and can no longer access group content
3. **Given** user in a group, **When** user sends text message, **Then** message appears in group chat for all members

---

### User Story 3 - Text Messaging via XMTP (Priority: P1)

Users in a group can send and receive basic text messages using XMTP protocol.

**Why this priority**: Establishes the core messaging infrastructure before adding file sharing capabilities.

**Independent Test**: User can send a text message via XMTP and other group members can receive it.

**Acceptance Scenarios**:

1. **Given** user in group, **When** user sends text message via XMTP, **Then** message is encrypted and delivered to all group members
2. **Given** user receives message, **When** XMTP connection fails, **Then** appropriate error is shown and message is queued for retry

---

### User Story 4 - File Attachment with Payment Gate (Priority: P2)

User attaches a file to a message and sets a payment price; other users must pay to access the file content stored on IPFS via Pinata.

**Why this priority**: Core value proposition of the application - paywalled file sharing.

**Independent Test**: User can attach a file (up to 50MB), set a price, upload to IPFS via Pinata, and other users see a payment prompt to access the file.

**Acceptance Scenarios**:

1. **Given** authenticated user in group chat, **When** user attaches file and sets price, **Then** file is uploaded to IPFS via Pinata and CID is sent via XMTP with payment prompt shown to other users
2. **Given** user viewing message with paid file, **When** user pays via x402 link, **Then** user can download file from IPFS via Pinata and no longer sees payment prompt

---

### User Story 5 - Payment Processing and Access Control (Priority: P2)

System processes x402 payments and grants appropriate file access based on payment status, with persistent download access.

**Why this priority**: Critical for the monetization aspect of the application and user experience.

**Independent Test**: User pays for a file once, download button appears, and can access it multiple times without paying again across sessions.

**Acceptance Scenarios**:

1. **Given** user who paid for file, **When** user returns to chat, **Then** user can access file via download button without payment prompt
2. **Given** user who hasn't paid for file, **When** user clicks payment link, **Then** x402 payment flow is initiated
3. **Given** user has paid for file in previous session, **When** user accesses chat in new session, **Then** download button is displayed instead of payment link

---

### Edge Cases

- What happens when a user's wallet transaction fails during payment?
- How does the system handle multiple simultaneous payments for the same file?
- What if the XMTP network is unavailable when sending/receiving messages?
- What happens if Pinata upload fails during file attachment?
- How does the system handle IPFS content unavailability after successful upload?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST implement wallet connection using standard Web3 providers (MetaMask, WalletConnect)
- **FR-002**: System MUST create and manage group chats with XMTP messaging protocol
- **FR-003**: Users MUST be able to send basic text messages to group members via XMTP
- **FR-004**: System MUST allow file attachments up to 50MB to be uploaded to IPFS via Pinata
- **FR-005**: System MUST generate x402 payment links for IPFS file access as specified in the protocol
- **FR-006**: System MUST track payment status per user and file to prevent duplicate payments
- **FR-007**: System MUST allow users to set arbitrary prices in ETH or test tokens for file access
- **FR-008**: System MUST display payment links prominently next to file names in chat
- **FR-009**: System MUST allow paid users to access IPFS files from Pinata without payment prompts
- **FR-010**: System MUST store and transmit only the IPFS CID via XMTP, not the file content itself
- **FR-011**: System MUST designate group creator as admin with ability to remove members
- **FR-012**: System MUST persist payment status across user sessions
- **FR-013**: System MUST replace payment links with download buttons for paid files

### Key Entities *(include if feature involves data)*

- **User**: Wallet address (identity), profile information, payment history
- **Group**: Unique identifier, member list (wallet addresses), admin (creator wallet address), creation timestamp, permissions
- **Message**: Sender (wallet address), recipient/group, content, timestamp, message type (text/file)
- **FileAttachment**: File metadata, IPFS CID, Pinata gateway URL, price, payment requirements
- **PaymentRecord**: Payer wallet, file identifier (CID), amount paid, transaction hash, timestamp, payment status

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Users can connect their wallet and authenticate within 30 seconds
- **SC-002**: Users can create a group chat and send their first message within 2 minutes
- **SC-003**: Text messages are delivered to all group members within 5 seconds
- **SC-004**: Files up to 50MB are uploaded to IPFS via Pinata and accessible within 15 seconds of upload
- **SC-005**: x402 payment flow completes successfully 95% of the time
- **SC-006**: Users who paid for a file can access it from IPFS via Pinata again without payment prompt 100% of the time
